Amazon SES mail tracking

Delivery and engagement observations for SES SMTP, durable recipient send journals, SQS event ingestion, and reviewed complaint suppression.

Configuration

Provision one event stack per Odoo database/environment using infrastructure/ses-events.json. Supply a unique NamePrefix and an existing operational AlarmTopicArn. Attach the returned RuntimePolicyArn to the runtime AWS identity. Credentials use boto3’s standard runtime chain; they are not stored in Odoo. Existing SES SMTP credentials remain unchanged.

The stack creates delivery-only and engagement configuration sets, SNS, SQS, dead-letter queues and alarms. It does not change sender identities, DNS, default identity configuration sets, or feedback forwarding. Use a verified identity in the same region. The runtime policy’s account-level SES operations use Resource “*” because suppression APIs do not support address resource ARNs.

In SES mail > Connections, enter the account, region, sender identity, configuration set names, topic ARN and queue URLs from the stack outputs. Choose a mail administrator with the SES mail administrator group. Use Check configuration, then Verify and enable. Select this connection on the intended outgoing SMTP server. Enabling a connection starts polling; attaching it to a server activates the SMTP guard. Do not attach an unverified connection to a busy server.

Keep both bounce and complaint suppression enabled. Keep existing email feedback forwarding until a controlled delivery/bounce/complaint test has passed. Monitoring must include both dead-letter queues. An event queue outage exceeding five minutes, stale suppression import or a nonempty processing dead-letter queue holds sends. Inspect, correct and redrive failed events; do not discard them to clear the hold.

Engagement uses a separate configuration set. Disable engagement at connection level for delivery-only operation. Authentication messages use delivery-only; links containing credentials are marked ses:no-track. Opens/clicks are observations, not proof of human reading. Some providers do not report complaints to SES.

Usage

Open Email delivery from a message action menu for recipient observations. Mail administrators review SES mail > Blocked addresses. Resolve a complaint only after documenting recipient permission. Uncertain sends need an explicit reviewed retry.

Development

The three addons are independent of general contact-role routing and campaign UI. OCA mail_tracking is pinned in repos.yaml. Its mail_tracking_mass_mailing bridge is shipped because it auto-installs when Email Marketing is present; no custom campaign feature is introduced by these addons.

Transactional flow: mail.mail is queued, then the scheduler prepares individual SMTP envelopes. Before SMTP IO an independently owned cursor commits an opaque recipient attempt. It never commits the caller’s transaction. Accepted copies are skipped on retry; ambiguous acceptance remains held for explicit review. This is not an exactly-once guarantee: an administrator-authorized retry of an uncertain attempt can deliver a second copy. Each such retry has a new token and preserves previous attempt history. Normal Odoo transaction tests use their rollback cursor; exercise the owned-cursor path separately before production.

SES tags correlate events to attempts. SQS events are source-validated, sanitized, deduplicated and persisted. A postcommit callback verifies durable persistence on a fresh cursor before acknowledging SQS. Redelivery is safe. Unknown correlations remain available for reconciliation, while complaints and permanent bounces still block their explicitly reported addresses. Do not map messages by address alone.

Tracking summaries never allow an open/click to overwrite a complaint or failure. The message action checks the caller’s access before constructing a transient recipient view. Raw operational models require administrator access. BCC is not exposed by the recipient view; this release does not provide a BCC composer.

Sanitized processed events expire after 90 days; accepted non-complaint journals after 365 days. Unresolved events, ambiguous sends and complaint records remain for review. Click URLs retain only the origin. IP addresses, user agents, raw payloads and message bodies are not copied into the event inbox.

Run Odoo with –test-enable and –test-tags /mail_composer_cc,/mail_composer_cc_account,/mail_tracking_ses against an isolated local database. Disable outgoing servers and cron workers before and after module installation. AWS calls and SMTP are mocked in the module tests; a captured MIME test validates actual envelope generation.

The owned-cursor smoke test must run outside Odoo’s transaction-test harness. Use an isolated database named erp_ses_test, with all cron workers and outgoing servers disabled, then run:

odoo shell -d erp_ses_test --no-http --max-cron-threads=0 < mail_tracking_ses/tests/owned_cursor_smoke.py

Supply your local database connection and addons-path options as needed. This script makes no AWS or SMTP calls and removes its test records.

Known issues / Roadmap

Deployment gate: verify AWS mailbox-simulator events and a controlled-inbox reply against the installed AWS stack before enabling a production server. Unit tests and CloudFormation validation do not substitute for this end-to-end check.

Optional follow-ups: SES API transport, campaign-specific statistics and consent, BCC UI, customer-role recipient routing, and attachment preview. None is required for the transactional SMTP integration.

Bug Tracker
